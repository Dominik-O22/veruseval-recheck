# Gate 2 batch brief: prove or refute regenerated VerusEval clause lemmas

You decide, with Verus as the only judge, whether each lemma below is TRUE (proved) or FALSE (refuted).
Each lemma is one rejected per-clause comparison from the VerusEval release, regenerated byte-for-byte
through the release's own per-clause path. You write the proofs and witnesses yourself. Do not run
any script that calls Claude or any LLM, and do not read or use any credential or token file.

## Your inputs
Your batch file lists one clause per line: `ID<TAB>direction<TAB>forms-to-do`.
For each ID, the harnesses are in `/work/harness/<ID>/`:
- `uncond.rs` (+ `uncond.json` with the lemma name and the clause texts) — the paper's unconditional lemma.
- `guarded.rs` (+ `guarded.json`) — the same lemma with the reference and generated `requires` added to the antecedent.
Each harness is a full Verus file: the reference program, wrapper spec fns `__sqm_antecedent_k_*` / `__sqm_consequent_1_*`, and at the end an empty `proof fn lemma_sqm_...(__arg0.., __ret0..) requires <antecedent wrappers> ensures <consequent wrapper> {}`.
Read ONLY the harness files of your own IDs (and this brief). Do not open anything under /work/release, /work/items, other batches' IDs, or other tasks.

Forms to do:
- `L1`: one form, use `uncond.rs` (the L1 antecedent is already the reference precondition).
- `same`: guarded and unconditional are one formula (no precondition on either side). One search on `uncond.rs`; the verdict counts for both.
- `uncond`: the guarded form is already proved (Verus accepts it with an empty body). Only the unconditional form remains.
- `guarded,uncond`: both. Do the guarded form first. If guarded is REFUTED, run the very same witness on `uncond.rs` (a guarded counterexample is also an unconditional one); that run normally settles uncond too. If uncond is PROVED, guarded follows by implication; record guarded as `proved` with `"propagated": "uncond"` after running the same proof once on guarded.rs (record its outcome either way).

## The checker (the only way to get a verdict)
Always `source /work/scripts/env.sh` first. Then:

    python3 -I /home/user/repo/analysis/gate2_check.py prove  /work/harness/<ID>/<form>.rs  PROOF.rs  [--rlimit 100]
    python3 -I /home/user/repo/analysis/gate2_check.py refute /work/harness/<ID>/<form>.rs  WITNESS.json
    python3 -I /home/user/repo/analysis/gate2_check.py sig    /work/harness/<ID>/<form>.rs   # params + wrapper calls

It prints one JSON line. Only `"outcome": "proved"` or `"outcome": "refuted"` is a verdict. `failed`, `timeout`, `rejected`, `void` are not.

PROOF.rs format: helper items (new proof fns / lemmas, may be empty), then a line `// ---- body`, then the statements that go inside the empty lemma body. The lemma statement is never changed. Forbidden anywhere in the proof text: `assume`, `admit`, `external_body`, any `#[verifier...]` attribute, `axiom`, `uninterp`, `unsafe`, `opaque`, `trusted` (the checker rejects these words even in comments or identifiers). Allowed: `assert ... by (nonlinear_arith)`, `by (bit_vector)`, `by (compute)`, `reveal_with_fuel`, `reveal`, induction via recursive proof fns with `decreases`, `assert forall ... by {}`, `#[trigger]`, `=~=`, calling vstd lemmas. `--rlimit 100` is allowed (it is a command-line flag). Do not copy reference spec fn definitions into helpers; refer to them by name.

WITNESS.json: literal values only, one per lemma parameter, as Rust exec-expression literals:
`{"__arg0": "vec![1i32, -2]", "__arg1": "&[3i32]", "__arg2": "3usize", "__ret0": "Some(0usize)"}`.
Allowed forms: numeric literals with suffixes (`5u64`, `-3i8`, `1.5f32`), `true/false`, chars, string literals, tuples, `vec![..]`, `&vec![..]`, `&[..]`, `Some(..)`/`None`, struct/enum literals (`Name { f: 1u8 }`, `Enum::Variant`), and for ghost types (int, nat, Seq, Map, Set) `5int`, `seq![..]`, `map![k => v]`, `set![..]`. Optional keys: `"_fuel": {"recursive_spec_fn": 6}` for reveal_with_fuel, and `"_types": {"T": "i32"}` to instantiate a generic lemma. The checker binds them in an exec fn with no loops, branches or calls, asserts each antecedent wrapper and the negation of the consequent, and separately checks that `assert(false)` does NOT verify in the same setting. Because values are built by exec code, a refutation is a real, representable input/output. Look at the wrapper spec fns to see exactly what the `__ret`/`__arg` parameters mean (some lemmas also carry old values of `&mut` args).

Tip: if an assertion of the antecedent fails on a correct witness because a quantifier or recursive spec fn is not unfolded, raise `_fuel`; for `forall`-shaped antecedents over small literal vectors Verus usually manages; for `exists`-shaped consequent negations, `!exists` must be proved, which is usually fine on short vectors. Floats (f32/f64) are largely uninterpreted in this Verus version: reason about lengths/indices where you can; otherwise the clause may end Undecided, which is an acceptable outcome.

## Budget and fairness (important)
Per form, stop at the FIRST verdict. Give each form a fair budget on both sides: try to refute as seriously as you try to prove. Read the clause, form a view, and try the side you think is right first, but before declaring Undecided you must have made at least 3 genuine refutation attempts AND at least 3 genuine proof attempts (genuine = a real candidate that you think could work, not a placeholder). Hard cap: 12 checker runs per form. If no verdict by then, the form is `undecided`. A timeout or failure is never a verdict. Never mark refuted from reasoning alone.

## What to record
Save every attempt as a file: `/work/attempts/<ID>/<form>/tNN_prove.rs` or `tNN_refute.json` (NN = 01, 02, ... in order across both kinds for that form; for `same` and `L1` use form `uncond`).
Append one JSON line per form to your log `/work/agent_logs/<batch>.jsonl`:

    {"id": "...", "form": "uncond|guarded", "covers": ["uncond","guarded"] or ["uncond"],
     "verdict": "proved|refuted|undecided", "try": <NN of the run that gave the verdict, or null>,
     "runs_prove": k, "runs_refute": m, "tool_calls": <all your tool calls spent on this form, incl. reads>,
     "rough_tokens": <your rough estimate of tokens spent on this form, input read + output written>,
     "file": "<path of the verdict file or null>", "propagated": null|"uncond"|"guarded",
     "note": "one line: the witness in plain words, or the proof idea, or why it stayed undecided"}

For `same`, put "covers": ["uncond","guarded"]; for `L1`, "covers": ["uncond"]. Write the log line right after each form finishes, so nothing is lost.

When the batch is done, reply with a short summary: counts of proved/refuted/undecided per form, and any problem with the checker or a harness (for example a harness that does not type-check, or a checker behavior that looks unsound). If you see something that looks like a soundness problem in the checker (e.g. a witness verifies that cannot be right), stop and report it instead of continuing.
